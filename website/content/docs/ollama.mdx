---
title: Ollama and llama.cpp
description: Run Ollama on a remote GPU through the CUDA shim, and what to expect.
---

Ollama runs models with llama.cpp, whose CUDA backend loads the CUDA runtime
and cuBLAS as shared libraries. Replacing those with the stand-ins sends its
GPU work to `rgpu-server`. Build the shim and the server first, as the
[CUDA shim](/docs/cuda-shim/) page describes.

This was checked with Ollama 0.40.0 and 0.40.3 and `qwen2.5:0.5b`, two ways:
with Ollama on the same Linux x86_64 machine as the server, and with Ollama in
a Linux arm64 container on a Mac reaching the server through an SSH tunnel.
Larger models have not been tried.

If the goal is only to use Ollama with a remote GPU, run Ollama on the GPU host
and point `OLLAMA_HOST` at it. That is full speed and needs none of this. The
steps below exercise the shim.

## Set up

Ollama loads its CUDA libraries from its own directory, so copy the
installation and swap them there. `LD_PRELOAD` on `ollama serve` is not enough,
because the libraries are loaded by a subprocess from a fixed path.

```sh
REAL=/usr/local/lib/ollama/cuda_v12          # Ollama's own CUDA 12 libraries
mkdir -p ~/ollama-rgpu/bin ~/ollama-rgpu/lib
cp /usr/local/bin/ollama ~/ollama-rgpu/bin/
cp -a /usr/local/lib/ollama ~/ollama-rgpu/lib/ollama
rm -rf ~/ollama-rgpu/lib/ollama/cuda_v13 ~/ollama-rgpu/lib/ollama/vulkan
cd ~/ollama-rgpu/lib/ollama/cuda_v12
rm -f libcudart.so.12* libcublas.so.12* libcublasLt.so.12*
cp ~/rgpu/build/libcudart.so.12 ~/rgpu/build/libcublas.so.12 \
   ~/rgpu/build/libcublasLt.so.12 ~/rgpu/build/libcuda.so.1 .
```

Start the server with the real cuBLAS libraries, then Ollama from the copy:

```sh
RGPU_CUBLAS=$REAL/libcublas.so.12 RGPU_CUBLASLT=$REAL/libcublasLt.so.12 \
LD_LIBRARY_PATH=$REAL ~/rgpu/build/rgpu-server &

GGML_CUDA_DISABLE_GRAPHS=1 RGPU_SERVER=127.0.0.1:9713 \
  ~/ollama-rgpu/bin/ollama serve
```

`GGML_CUDA_DISABLE_GRAPHS=1` is required. llama.cpp otherwise uses CUDA graph
capture, and the shim does not implement `cudaGraphExecUpdate`.

Ollama's log should name the GPU under `inference compute`, with
`library=CUDA`. If it says `library=cpu`, a stand-in failed to load and Ollama
fell back to the CPU without an error.

## What to expect

With Ollama on the same machine as the server:

- **Results.** With llama.cpp's server run directly at temperature 0, 320
  generated tokens matched the native run exactly.
- **Round trips.** One per generated token, the download of the result.
  Without the default [`RGPU_LAZY_SYNC`](/docs/configuration/) rule it is 21.
- **Speed.** On the one host measured, an RTX 4090, 43 to 48 tokens per second
  against 154 native, about 3.4 times slower, with client and server on the
  same machine. The gap is per-call work on the client, which has not been
  profiled, and it varied between hosts in earlier builds. Over a network, add
  about one round trip of latency per token.
- **Cleanup.** A client killed mid-run has its GPU memory released when its
  session expires.

## Over a network

The link sets the pace. From a Mac to a GPU 123 ms away, with
1.5 MiB/s of upload:

- **Loading** took about seven minutes: the model's weights, 374 MiB here,
  are uploaded through the tunnel. Ollama gives a load five minutes by
  default, so set `OLLAMA_LOAD_TIMEOUT=30m` or the load is abandoned.
- **Generation** ran at about 3 tokens per second. Each token is one round
  trip, and llama.cpp downloads the model's full output for it, 0.58 MiB for
  this model, to choose the token on the client.
- **Results** matched the native run exactly, across the two machines and the
  two processor types.

In the container, copy the stand-ins from an arm64 build of the shim
(`./scripts/build_client.sh` makes one), skip the server step, and point
`RGPU_SERVER` at the tunnel, such as `host.docker.internal:9713`.
